# 모델 선정 의사결정

> 본 프로젝트의 LLM으로 Gemini (`gemini-3.1-flash-lite`)를 선택한 의사결정 과정을 기록한 문서입니다.

---

## 1. 결론

본 프로젝트는 LLM으로 멀티모달을 지원하는 **Google Gemini**를 선택했으며, 그중에서도 비용과 응답 속도를 고려해 **`gemini-3.1-flash-lite`** 모델을 사용했습니다.

---

## 2. 모델 선정 기준

본 프로젝트에서 LLM이 충족해야 했던 요구사항은 다음 세 가지였습니다.

### ① 멀티모달 데이터 처리

레시피 콘텐츠는 두 가지 형태로 들어옵니다.

- **YouTube 영상 URL**: 음성, 자막, 화면(시각 정보)
- **블로그 URL**: 본문 텍스트와 이미지

영상의 음성과 시각 정보를 LLM이 직접 분석해야 했기 때문에, **하나의 모델이 영상, 텍스트, 이미지를 모두 처리할 수 있는 멀티모달 입력 지원**이 필수였습니다.

### ② 구조화 출력 지원 (JSON)

추출 결과를 조리 UI에서 그대로 렌더링하기 위해, LLM의 응답은 정해진 JSON 스키마를 따라야 했습니다.

자유 형식의 자연어 응답을 텍스트 파싱해서 사용하는 방식은 응답 구조가 달라질 경우 후처리 로직이 불안정해질 수 있으므로, JSON 스키마 기반의 Structured Output 기능 지원이 필수였습니다.

### ③ 지연 시간 및 비용 최적화

본 프로젝트의 LLM 호출은 사용자가 URL을 입력하는 순간 발생하는 **인라인 호출**입니다.

응답이 느리면 사용자가 이탈할 가능성이 커졌습니다. 실제로 현재도 평균 응답 시간이 약 19초 수준이어서, SSE 기반 진행률 UI로 사용자 경험을 보완하고 있습니다.

따라서 **빠른 응답 속도와 저렴한 비용 단가** 모두를 만족해야 했습니다.

---

## 3. Gemini를 선택한 이유

모델 선정에서는 추상적인 "성능 순위"보다, 본 프로젝트의 요구사항인 멀티모달 입력, 구조화 출력, 빠른 응답 속도에 대한 적합도를 우선적으로 평가했습니다.

세 가지 조건을 모두 만족하는 모델을 탐색한 결과, Gemini가 가장 적합한 선택지였습니다.

- 당시 검토한 주요 LLM 중 **YouTube URL 또는 영상 파일을 직접 입력으로 받아 음성과 화면 정보를 통합 분석하는 기능**을 정식 지원하는 모델은 Gemini가 가장 넓은 지원 범위를 갖추고 있어, 본 프로젝트의 레시피 영상 처리 요구사항과 정확히 맞아떨어졌습니다.

- 또한 `responseSchema` 기반 Structured Output을 제공하며, Flash 계열 모델은 비용과 속도 모두에서 경쟁력이 있었습니다.

Gemini 패밀리 내에서는 비용 효율성을 우선해 **`gemini-3.1-flash-lite`** 를 선택했습니다.

추출 작업은 비정형 콘텐츠를 정해진 JSON 구조로 변환하는 비교적 정형화된 태스크였습니다.

또한 시스템 프롬프트의 핵심 규칙만으로도 충분한 품질 확보가 가능했기 때문에, 더 비싼 Pro 계열 모델의 비용을 쓰기엔 아까웠습니다.
